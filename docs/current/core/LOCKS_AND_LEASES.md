# Locks, leases, claims and markers

Status: implemented. Line numbers are for code at main `0dac86fa`.

This is the catalogue of every coordination key the pipeline writes to the shared DynamoDB table (`CACHE_TABLE`, `dev-wwii-api-cache`, partition key `cache_key`, TTL attribute `ttl`: `cloudformation/storage.yaml:221-225`) and every S3 object used as a marker. It answers three questions for each one: who writes and reads it, what clears it, and what to do when it is stale.

Related docs, not repeated here:

- NAT demand, teardown triggers and the networking state machine: [NETWORKING_LIFECYCLE.md](../NETWORKING_LIFECYCLE.md)
- Concurrency design and the credit-gate design: [CONCURRENCY_AND_NAT_SPEC.md](../dataquality/CONCURRENCY_AND_NAT_SPEC.md)
- Operator commands to list and delete locks and queues: [RUNBOOK.md](../RUNBOOK.md) (sections "Clear Locks", "Clear Pending Queues")
- What a document passes through from upload to done: [DOC_LIFECYCLE.md](DOC_LIFECYCLE.md)

## 0. Rules that apply to every row

- DynamoDB TTL deletion is eventually consistent and can lag by hours (`lambda_handlers/batch_poller.py:406-407` says up to two days). Every reader that cares filters an expired row by comparing `ttl` to now in code (`src/utils/nat_lease.py:98-127`, `lambda_handlers/idle_backstop_reaper.py:117`). A row with no `ttl` attribute lives until something deletes it.
- All keys are plain table rows. The table also holds Grok answer cache rows (`cache_backend.py:119`, `ttl_days`), search cache rows (`search#<source>#<hash16>`, `src/utils/search_cache.py:52`) and `metrics#<batch_id>` rows (`src/grok_client.py:386-391`, 90 days). Those are caches, not coordination, and are not listed below.
- Scans filter on `begins_with(cache_key, ...)`. Scan `Limit` is applied before the filter, so a reader that sets one can miss rows. The idle reaper documents this and paginates fully (`idle_backstop_reaper.py:68-80`).
- `scripts/e2e_reset_data.py:38-60` lists the prefixes an operator reset wipes: `title# source# pending# manifest# book_manifest# lock# batch_job# nat#` always, plus `dedup_run# reaper# doc# gate# ocr# ocrctl# oom# retrieve# reviewed#` with `--full`. Use that list to check this catalogue for a missing prefix.
- `src/utils/file_lock.py` is not part of this catalogue. It is a local filesystem lock (`flock` on a sidecar `<path>.lock`, `file_lock.py:117-145`) inside one task's working directory. Nothing in it touches DynamoDB or S3.
- `src/utils/batch_rounds.py` holds per-run round counters in memory and writes no keys.

## 3. Where the Grok answer cache lives

Grok answers are cached in the same table with the key and `ttl` written by `src/utils/cache_backend.py` (`cache_backend.py:119`, `ttl_days`). Those rows are not coordination keys. ## 4. Findings from this review

These are facts found while reading the code. None is fixed here.

1. **Dead lock code.** `ecs_entrypoint._acquire_lock` (4069) and `_clear_all_locks` (4112) have no callers. The only lock writer for phase families is the trigger Lambda. The docstring of `_lock_key` and `RUNBOOK.md` still read as if the task took the lock.
2. **Phase 3 lock status write can create a bare singleton row.** `phase3_enrich_data._update_lock_status` (`phase3_enrich_data.py:54-72`) updates `lock#<env>-wwii-phase3-enrich` even when multi-doc mode holds the per-book key `...#<book>`. `update_item` creates the singleton row with `status` only and no `ttl`. Nothing deletes it (the task's `_remove_lock` deletes the per-book key), and `nat_teardown` and the reaper count any `lock#` row as demand. This applies only when `MULTI_DOC_ENABLED` is true and the task runs in ECS. UNVERIFIED at runtime: not reproduced.
3. **Docs left at `running`.** `_claim_doc` writes `claimed_at`; no code reads it, and the state machine's `DocFailed` state does not touch the record (`dispatcher.yaml:316-322`).
4. **`human_gate` is not wired in.** See the `gate#` row.
5. **`batch_job#` rows are never removed.** `job_queue.remove_job` has no caller outside tests.
6. **`credit#spend` only accumulates.** See the row and `TODO.md:930`.
